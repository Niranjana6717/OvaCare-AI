# OvaCare AI — Clinical Safety

## The chain this product must never collapse

```
Health Tracking → Educational Information → AI-Assisted Screening →
Professional Medical Evaluation → Clinical Diagnosis
```

OvaCare is at the third step. It does not perform, and does not claim to
perform, the fourth or fifth. Every control in this document exists to keep
that boundary from being crossed by an engineering shortcut, a UI copy
change, or a model update.

## 1. Wording control (requirements #62–64, #90 tests 1–2)

`backend/app/safety/wording.py` is the **single source** of every
user-facing string connected to a screening result, cycle estimate, or
notification. Services import from it; they do not construct their own
phrasing. On top of that, `assert_safe_wording()` is a runtime guard —
called on every outbound result string in `prediction_service.py` and
`notification_service.py` — that raises if the text matches a banned
pattern (`"you have pcos"`, `"you do not have pcos"`, `"this proves"`,
`"you are healthy"`, `"no need to see a doctor"`, etc.). This is
defense-in-depth: the primary control is "there is only one place text
comes from"; the guard exists so a future code change that bypasses that
place fails loudly in tests rather than shipping.

**Verified for real**: `backend/tests/test_safety_wording.py` (10 tests) —
directly checks the low-indication text never says "No PCOS," the
high-indication text never says "You have PCOS," and that
`assert_safe_wording` actually raises on constructed bad strings and
passes every approved string.

## 2. No automated diagnosis (requirement #65)

The model outputs exactly one of three `ScreeningOutcome` values —
`higher_indication`, `lower_indication`, `insufficient_data` — never a
diagnosis, a medication recommendation, or a claim to replace labs/
ultrasound/clinician assessment. There is no code path anywhere in
`app/ml/` or `app/services/prediction_service.py` that outputs free-text
generated by the model itself; all narrative text is the static, reviewed
strings from `wording.py`.

## 3. No false reassurance (requirement #64)

`SCREENING_RESULT_TEXT["lower_indication"]` explicitly states "This does
not rule out PCOS or other health conditions" — a lower result is never
phrased as "you're fine." Verified by
`test_lower_indication_never_says_no_pcos`.

## 4. Red-flag safety rules (requirements #66–68)

`backend/app/safety/red_flag_rules.py` is a **separate, deterministic,
human-readable ruleset** — not derived from or dependent on the ML model.
`app/services/assessment_service.run_safety_and_prediction()` runs the
safety check and the ML prediction from the same input, and returns the
safety result regardless of whether the ML call succeeds, is unavailable,
or reports `insufficient_data` — an urgent flag is never suppressed by an
ML-side failure.

Current rules (RF-001–RF-004): severe bleeding (soaking through
protection hourly, or with fainting/dizziness), maximum-severity pelvic
pain, fainting/severe dizziness, chest pain or breathing difficulty. Each
only ever triggers the generic `URGENT_SAFETY_MESSAGE` — **the ruleset
never attempts to name a cause**, which is what keeps it on the
"recognize and point to care" side of the line rather than the "diagnose
the emergency" side.

**`RULESET_REVIEW_STATUS = "pending_clinical_review"`** — stated plainly in
`red_flag_rules.py` itself. No qualified clinician has reviewed this
ruleset in this project's development process. It must not be described as
clinically reviewed until that review has actually happened, with a real
reviewer identity and date recorded (see §6).

**Verified for real**: `backend/tests/test_red_flag_rules.py` (11 tests) —
each rule fires on its trigger and stays silent otherwise; irregular-cycle
data alone (`cycle_regularity: "irregular"`, high variability) triggers
**zero** flags, proving irregularity is never treated as an emergency or
folded into a diagnosis (requirement #83); the integration-level
`safety_service.check_for_red_flags()` never mentions "pcos" in its
message.

## 5. Never fabricate a prediction (requirement #54, #90 test 3)

The single most load-bearing rule in this codebase. `app/ml/predictor.py`
has exactly three exit paths and no fourth:
1. No production model artifact loaded → `insufficient_data`.
2. A model is loaded but a required field is missing or a required numeric
   field is outside the range the model was validated on → `insufficient_data`.
3. Complete valid input → the model actually runs, and the returned
   probability, outcome, and explanation all come from that run.

**Verified for real, end-to-end, against an actually-trained scikit-learn
pipeline** (not a mock): `backend/tests/test_predictor_never_fabricates.py`
(5 tests). See `docs/ml_documentation.md` §6 for exactly what that proves.

This is also enforced at the **database** level, independent of the
application code: `predictions.chk_probability_matches_outcome` rejects any
row where a non-`insufficient_data` outcome has a null probability, or an
`insufficient_data` outcome has a non-null one. Verified against a real
PostgreSQL instance — see `docs/database_design.md`.

## 6. Content review tracking (requirement #69)

`backend/app/safety/content_review.py` maintains a registry of every
reviewable health-meaning surface (screening wording, the red-flag
ruleset, questionnaire wording, educational content, the medical
disclaimer), each with a `review_status` that starts **honestly at
`pending_review`** — nothing in this codebase defaults to "approved."
`is_content_approved(content_id)` is the one function that should gate any
future "clinically reviewed" badge in the UI; nothing currently calls it to
claim that status, because no such review has occurred in this project's
development process. Filling in `reviewed_by_role` / `reviewed_at` for a
real review is the explicit trigger to flip an entry to `"approved"`.

## 7. Human oversight (requirement #78)

No code path in this repository automatically promotes a model to
production (`docs/ml_documentation.md` §3), automatically flips a content
review to `approved`, or represents an AI output as an authoritative
medical decision. Every one of those is a deliberate, separate, human step
this codebase creates the *record-keeping* for but does not perform on its
own.

**Note on tests 6 and 7's coverage**: both `notification_service.py` and
`prediction_service.py` import SQLAlchemy at module scope, so — like the
rest of the FastAPI/SQLAlchemy backend — they cannot be imported directly
in this sandbox (see `docs/deployment.md` §1). Rather than leaving these
two as unexecuted gaps, each got two real, executed checks instead of a
literal call into the SQLAlchemy-dependent function: (a) a static-analysis
check (Python's stdlib `ast` module) on the relevant function's source,
proving `get_display_text()` genuinely branches on `privacy_mode` rather
than returning a constant, and proving `build_result_payload()` never
calls back into the model layer — the exact code path that could silently
recalculate a historical result; and (b) a behavioral check exercising the
real underlying mechanism through code that IS dependency-free
(`app.safety.wording`'s exact private-text string and safety-wording
guard for test 6; `app.ml.predictor.run_prediction()` against two
differently-versioned real model artifacts for test 7). The full
ORM-level round trip (an actual `Notification`/`Prediction` row) remains
in the written-but-unexecuted pytest suite (tests 8-10 above), same
disclosed status as the rest of that suite.

## 9. Before production (requirement #92)

None of the following may be claimed until actually true: "medically
validated," "clinically validated," "approved," "certified," "regulatory
compliant." Before OvaCare is presented as a real-world health product,
review: the dataset's license (`docs/ml_documentation.md` §1.3), the
red-flag ruleset (§4 above), the threshold selection
(`docs/ml_documentation.md` §4), the questionnaire and educational content
wording, retention/deletion behavior, and applicable regulatory
requirements in the intended deployment market(s) (e.g. HIPAA if deployed
in the US handling PHI, GDPR-equivalent obligations elsewhere) — none of
which this codebase asserts compliance with today.
